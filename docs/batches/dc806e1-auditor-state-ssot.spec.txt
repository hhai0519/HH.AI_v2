2. **載明基準 Commit（Base Full OID）與目標檔案範圍（EXACT_SPEC 另需批次規格或 SHA）**，不再要求手寫檔案總行數作為 blocking truth。執行者於執行前確認工作區乾淨且 HEAD 與基準一致。
3. 修改指令依模式區分：**EXACT_SPEC 必須以批次規格（Batch Spec）的 structural anchor 原文為主**；**GOAL_SPEC 則提供目標架構、變更邊界與驗收準則**，由執行者自主決定實作方式。若有行號僅作為輔助 diagnostic，不得作為 blocking truth。
4. 驗證步驟要求**回報確定性工具與 Gate 的執行輸出**（如 validate_skills, check_consistency, fingerprint, pytest）；命中檔名與行號等由機器輸出提供，提示詞不作人工預測。
5. `git add` 一律明確路徑，禁止 `-A` 與 `.`。GOAL_SPEC 模式下不要求 Auditor 預先列出 exact file list，實際提交路徑由執行者自 diff 產生逐檔 explicit git add。
6. 結尾固定要求純文字回覆與「以上是 Antigravity IDE Agent 的回覆」。
7. **回報負擔要二擇一**：要求 `git diff` 原始輸出時，
   就**不要**同時要求既有檔案的全文——diff 已能證明「改了什麼」且無法造假，
   全文是冗餘的。只有新建檔案才需要貼全文。
   2026-09-01 曾因同時要求兩者，回覆過長而導致執行端以摘要代替，
   使 diff 機制歸零（見 `docs/refactor-backlog.md` 第 24 點 C 段）。
8. **每份提示詞都必須包含三項更新指令：交接區、`docs/TASKBOARD.md`、
   `docs/AUDIT-LOG.md`**（見 §9.3、§10.5、§7.1），
   與更新 `docs/refactor-backlog.md` 同級。
   TASKBOARD 要更新的內容：受影響項目的狀態流轉、新發現的缺口登錄、
   可封存項目的建議，**以及「最後更新」那一行的 HEAD**。
   2026-09-02 的複驗兩度發現同一個失效模式：規則只寫在 §9.3／§10.5，
   而審計官實際照著跑的清單是本節——規則不在執行路徑上。
   第一次是交接區，第二次是 TASKBOARD，後者導致看板在建立後三批就已過期。
9. **確認執行者本機與遠端同步**：提示詞的工作目錄段落必須要求
   執行者先 `git pull origin main` 並確認 HEAD 與提示詞假設的一致。
   2026-09-02 曾發生本機落後遠端一個 commit，若未察覺，
   所有行號基準都會錯。
10. **提示詞開頭要求執行者從檔案讀取規則，不依賴自動載入**：
    必須包含一段「動手前必讀」，要求執行者執行
    `cat .agents/rules/prompt-preflight.md` 等指令並貼出輸出。
    2026-09-02 發現 Antigravity 的 session 變長時會清掉對話前綴
    （畫面顯示「The server cleared a prefix of the conversation」），
    **自動載入的規則可能已被丟出 context 而執行者不自知**。
    這是「規則存在、也載入了，但被 context 截斷丟掉」的第三種失效形態，
    前兩種是「不在執行路徑上」與「沒有偵測」。
11. **配對與覆蓋**：更新 `TASKBOARD.md` 的 HEAD 時，必須同時更新交接區
    §5.1 第一行的 HEAD；`git add` 清單的每個非 exempt 檔案，都要同時出現在
    Allowed Scope、批次規格修改目標與 Gate 驗證清單中。完整規則見
    `.agents/rules/prompt-preflight.md` §3.1、§3.2。覆蓋檢查以 scope/spec/git-add
    為準，不得再依賴手寫行數清單。
12. **每份提示詞必須包含「審計官自檢聲明」區塊**，
    逐項列出 `handover-selftest.md` E 節的自檢結果。
    **這是自檢唯一的外部產物。**
    2026-09-02 稽核發現：E 節是審計官唯一的自檢清單，
    但它不產生任何可觀察的東西——有沒有跑過，使用者看不到、
    執行者看不到、repo 裡沒有痕跡。
    **一個沒有產物的自檢等同不存在**（`PRINCIPLES.md` §2.8）。
    這正是審計官連續多批未遵守 §6.1 卻無人察覺的根本原因，
    不是自律問題，是設計上無法被觀察。
    執行者對該區塊做機械交叉驗證，規則見
    `.agents/rules/prompt-preflight.md` §3.4。
13. **每個錨點對應本批 base commit 與規格上下文**（僅 EXACT_SPEC 適用；GOAL_SPEC 標記為 N/A），在目標檔案中具備結構唯一性
    （machine count == 1），不依賴特定 clone 第 N 行作為 blocking truth。
14. **寫入含 `§X.Y` 的文字時，若引用的是他檔章節，必須在同一行寫出檔名。**
    CHECK 10 把未標明檔名的 `§X.Y` 視為同檔引用，找不到就 FAIL。
    2026-09-05 §6.6 的新文字因混用同檔（§5.5／§5.6）與跨檔
    （`prompt-preflight.md` §3.3／§3.4）引用而觸發 CHECK 10——
    **審計官寫的規則觸發了審計官建的檢查器**。
15. **每個插入型修改若涉及結構序列，必須附明確驗收準則**（例如小節或項目序列應嚴格遞增）；
    不得將 LLM 預測所有 post-state 衍生序列當作通用 blocking requirement。
16. **每份提示詞必須包含「機械前置證據與邊界宣告（Mode-Aware Preflight）」**：
    所有模式共同包含：(a) 基準 Commit Full OID；(b) 批次模式（`batch_mode`，明確標記 GOAL_SPEC 或 EXACT_SPEC）；(c) 允許修改範圍（Allowed Scope）；(d) 標準驗證指令與 Gate 清單。
    只有 EXACT_SPEC 模式才需附帶批次規格路徑與規格 SHA-256；GOAL_SPEC 模式則載明目標、不變量與驗收準則。
    執行者交叉驗證規則見 `.agents/rules/prompt-preflight.md` §3。
    **刪除手寫檔案行數、圍欄數與結構快照的 blocking 要求。**

17. **提示詞若包含任何「移除」，必須附上移除前複查的三步結果**。
    移除包含：刪除檔案、刪除章節、刪除規則、把看板項目移出看板、
    搬到歸檔區之後刪掉原處。三步為：反向引用掃描、唯一內容確認、
    **重新讀檔的獨立複查**。原則本體見 `PRINCIPLES.md` §2.9。
    複查結果要逐項寫進提示詞，讓執行者能機械比對，
    不得只寫「已確認無引用」。
    **理由**：本專案的六次局部虛構全部發生在「憑記憶重述內容」上。
    移除是不可逆的，而判斷「這段內容別處也有」如果來自記憶而非磁碟，
    錯了就永久遺失。2026-09-01 的
    `SOP_00_Skill_Lifecycle_Management.md` 事件即為實例：
    去向被概括寫成「已拆分為 ADR-0013 與兩份 rules」，
    實際上第一至第四節從未遷移也未淘汰（見 `docs/ARCHIVE-INDEX.md`）。

18. **提示詞若為 EXACT_SPEC 且修改規範層檔案，必須以同一份批次規格進行模擬，並以確定性工具輸出為準**。
    審計官在 EXACT_SPEC 產出提示詞前，使用 `scripts/build_prompt_evidence.py`（BPE）驗證規格與模擬，但**不得將套用後行數、圍欄數、項數或預測輸出預抄至提示詞作為 blocking truth**。GOAL_SPEC 模式由驗收測試與 `scripts/verify_all.py` 守護，不要求虛假規格模擬。
19. **提示詞中的不可變常數（base OID、spec SHA、allowed scope 等）必須有明確來源；
    derived values 不得進 prompt 成為 blocking truth**。
    基準 commit 必須等於執行者在第 0 步實測的 HEAD。指不出產生者的不可變常數即為模型編造，
    必須刪除或重測；而由機器計算的衍生值（行數、圍欄數、test count、CHECK count 等）交由確定性工具產出，
    不作為提示詞 blocking truth。原則本體見 `PRINCIPLES.md` §2.10。

20. **每份提示詞必須包含補打 `audited-*` tag 的指令。**
    §11.3 規定每批核對通過後在下一批打 tag，但該規則從未寫進本節——
    **這是 §5.7「規則的層級決定它會不會被執行」的第八次**。
    前三次分別是交接區、`docs/TASKBOARD.md` 與 `docs/AUDIT-LOG.md`，
    各導致該檔落後一至三批；這一次落後七批。
    2026-09-07 實測：時序最新的 tag 為 `audited-e6f543a`（2026-09-05），
    其後七個已核對通過的批次全數無 tag，
    且 `scripts/` 與 `.github/` 全庫查無 `audited-` 字串，偵測從未實作（B-12）。
    指令固定兩條，**且都必須明確帶上目標 commit**：
    `git tag audited-<上一批的 hash> <上一批的 hash>` 與
    `git push origin audited-<上一批的 hash>`。
    **省略第二個參數會打在當下的 HEAD 上**——tag 名字對、指向錯。
    2026-09-11 實測 17 個 tag 中有 9 個如此，成因正是原措辭沒寫目標參數。
    機械守衛為 `scripts/check_consistency.py` 的 CHECK 18（tag 名實比對）；
    九個歷史錯 tag 的修復程序見同檔 §11.6，需使用者明確授權。
    驗證步驟必須要求貼出 `git tag -l "audited-*"` 的實際輸出，
    只回報「已補打」不算數。打不打的判準見 §11.4。


21. **EXACT_SPEC 批次的規格必須以 repo artifact 形式交付，並使用 BPE 進行驗證與模擬。**
    規格存放於 `docs/batches/<base-hash>-<slug>.spec.txt`，載明 `HEAD: <base-hash>`。
    規格格式由 `parse_spec` 與 `apply_mod_to_text` 解析，支援 `insert_after`、`insert_before`、`replace`、`create_file` 等 mode。
    審計官在產出 EXACT_SPEC 提示詞前，執行 `python scripts/build_prompt_evidence.py <spec_path>`（BPE）驗證錨點唯一性並計算規格 SHA-256。
    **GOAL_SPEC 模式不強制要求 Batch Spec**，其完成證據由 git commit 紀錄、測試通過輸出與 Actions 綠燈構成。
    只存在於對話或 `/tmp` 的規格視為不存在。CI 上的 CHECK 17 會在 parent commit 基準上重放規格並逐位元比對。
    規格與 CI 對應方式、命名規則與單一 commit 原則見 `docs/batches/README.md`。

    **單一原則：提示詞不得寫入任何由機器直接產生的衍生數字作為 blocking truth。**
    套用後行數、圍欄數、錨點行號、測試總數、CHECK 總數、技能總數，
    一律由 `scripts/build_prompt_evidence.py` 與各驗證腳本在執行當下產生。
    審計官把這些值抄進提示詞的那一刻，就多了一次抄錯的機會。
    **正確作法是把規格交給執行者，由確定性工具消費同一份規格、產出機械事實。**
    執行者側的對應規則與錯誤分級見 `.agents/rules/role-boundaries.md` §7。
### 6.2 零命中類的驗證條件，必須先列出自身指令造成的例外

寫「某字串應為零命中」之前，先檢查自己的指令內容是否會產生該字串。

**這條有兩次失敗紀錄**：一次是「四個字串零命中」但替換文字本身含該字串；
一次是簡體字檢查，而修改說明裡就寫著要被修正的那個簡體字。
兩次都造成執行端面對一個設計上不可能通過的條件。

### 6.3 一次只給一份，一鍵複製

單一完整區塊，不分段讓執行端拼接。

### 6.4 每次回覆結尾附下一批提示詞

除非需要使用者裁決或提供資料，該輪才改為列出待確認事項。

### 6.5 驗證步驟要設計攔截點

只問「有沒有做」抓不到「只做一半」。驗證步驟要設計成
**做一半就會露出來**的形式。

作法：要求執行者**貼出整節內容並確認共 N 項**，
而不是問「第 8 項加了嗎」。若他只加了第 8 項漏掉第 9 項，
項目數對不上，當場就會被發現。

同類手法還有：要求貼出章節標題的完整序列（跳號即異常）、
要求貼出殘留檢查的實際命中清單（只回報「零命中」等於沒驗證）。

> [!WARNING]
> **攔截點屬於驗證設計，不是規範內容。**
> 提示詞裡出現的「應為九項」「應為 16 個檔案」這類數字，
> 是為了讓遺漏可偵測而設，不代表那個數字本身有規範意義。
> 日後讀到舊提示詞時不要把攔截用的數字誤當成規則。

### 6.6 每個錨點都要驗證唯一性

寫進提示詞的每一個錨點文字，**產出提示詞之前**必須逐一驗證：

    import io
    t = io.open(目標檔案, encoding="utf-8").read()
    print(t.count(錨點字串))   # 必須恰好是 1

count 為 0 代表錨點不存在，大於 1 代表會改到錯的地方。

**失效紀錄**：2026-09-02 連續三次錨點失誤，成因各不相同：

| 次 | 錨點 | 成因 |
|---|---|---|
| 1 | `HANDOVER.md` = 848 行（實為 847） | 用推算代替實測 |
| 2 | 交接區 HEAD = `d1e389b`（實為 `aa36448`） | 前一批漏了更新，審計官的假設過期 |
| 3 | backlog 第 34 點結尾（該字串不在該檔案中） | **跨檔案汙染**——把 `auditor-protocol.md` 檔尾的一句話，當成 `refactor-backlog.md` 的內容 |

第三次的直接成因是：取錨點時在同一條指令裡輸出多個檔案的片段，
然後從一堆輸出中憑肉眼挑選。**往後取錨點一律逐檔進行，並用 count() 驗證。**

**錨點的選擇要依「插入的位置」決定，沒有一體適用的規則**：

| 情境 | 正確錨點 |
|---|---|
| 在某節**末尾**新增同層級小節 | 錨在**該節的最後一行內容**，插在其後 |
| 在某節**開頭**新增內容 | 錨在該節的標題行，插在其後 |
| 新增**一級章節** | 錨在下一個一級標題，插在其前 |

**「錨在下一個標題並插在其前」只適用於新增一級章節。**
用在新增同層級小節時，必然造成編號逆序——
2026-09-04 與 2026-09-05 各發生一次：
`prompt-preflight.md` 的 §3.4 錨在同檔 §3.3 之前，造成 3.2 → 3.4 → 3.3；
§5.6 錨在 §5.5 之前造成 5.4 → 5.6 → 5.5。
兩次都由執行者依 `prompt-preflight.md` §3.3 分類為【疑問】並停下回報，
未造成實際寫入。

**第二次的成因是本節原本的建議**——它寫「下一個標題行通常唯一且不需要判斷，
優先用它」，沒有區分一級與同層級。規則本身就是元凶時，
改的是規則，不是叫自己下次小心。
第三次失誤若當初用「插在 `## 四、更新紀錄 (Update Log)` 之前」，
就不會發生。

### 6.7 修改既有敘述前，先搜尋「這件事」在哪些地方被描述

§6.6 要求驗證錨點唯一性，但那只防「錨點找不到」，
**防不了「錨點找得到，但同一件事還有別的地方也要改」**。

因此在寫修改指令之前，除了驗證錨點，還要搜尋**主題**：

- 要改某個 commit 的核對狀態 → 搜尋該 hash 在全庫的所有出現位置
- 要改某個數字 → 搜尋該數字的所有出現位置
- 要刪某個章節 → 搜尋誰引用了它（`§X.Y` 形式）
- **要改程式碼中的顯示字串** → 搜尋是否有測試斷言引用它。
  2026-09-06：修改 CHECK 8／9 的 FAIL 訊息，未查證兩個測試正斷言在該字串上，
  且錯誤判定「不改變行為」。實測移除後為 `2 failed, 64 passed`。
- **要設計跨環境的比對** → 先查該環境會改動什麼。
  2026-09-06：指紋的 sha256 讀原始位元組，未考慮 Windows Git
  `core.autocrlf` 會把 LF 轉 CRLF，CI 上線首日即紅燈，42 檔 sha256 不符。
- **要偏離任何一條規則** → 先查那條規則有沒有機械守衛。
  2026-09-06：宣告不更新 `docs/AUDIT-LOG.md`，未查證本節所屬協定的
  §6.1 第 8 項由 CHECK 12 守著，等同主動製造一個必然的 CI 失敗。
- **要移除任何本體** → 依 `PRINCIPLES.md` §2.9 完成三步複查。

**搜尋的是「事」，不是「字串」。** 同一件事可能用不同措辭描述。

**失效紀錄（五次，同一根因）**：

| # | 事件 |
|---|---|
| 1 | 宣告「7 個檔案」，實際 6——只數自己經手的，未回頭盤點全庫 |
| 2 | 宣告「15 個檔案」，實際 16——同上 |
| 3 | 改了 §9.5 說自測清單進 repo，但 §5.2 仍寫「刻意不進 repo」 |
| 4 | 刪除交接區 §5.2 的清單，但 §9.4 第 3 項仍指向它 |
| 5 | 更新交接區 §5.1 時只替換第一個項目符號，最後一個仍說「尚待核對」，造成同一批既已通過又待核對 |

第 5 次的危害最直接：交接機制的核心是「比對 HEAD 判斷有無未核對批次」，
而那一節自己的敘述互相矛盾。

**規劃機械檢查（CHECK 15）**：交接區 §5.1 中，
同一個 commit hash 不得同時出現在「已核對通過」與「尚待核對」的語境。

## 7. 自我審查

觸發時機、檢查項目與外顯要求見 `PRINCIPLES.md` §4。

**觸發時機以 §4.1 的五條為準，不是「每則回覆」。** 但一旦觸發，
§4.2 的六個檢查項目就要逐項寫出，不得只寫「已檢查」。
`PRINCIPLES.md` §4.1 第 1 項是「每一批工作 push 完成、產出核對報告時」——
**實務上等於每一批核對都要做一次。**

### 7.1 證據必須落地成檔案

檢查點的結果除了寫在回覆中，還要追加一列到 `docs/AUDIT-LOG.md`。

理由：寫在回覆裡的東西不進 repo，下一個 Agent 看不到，
也無從判斷上一任有沒有做。**沒有留下證據的控制，等於沒有控制。**

`AUDIT-LOG.md` 的最新一列 commit 若落後於實際 HEAD 超過一批，
即代表有批次未做檢查點。這是可機械檢查的（規劃為 `check_consistency.py`
的 CHECK 12）。

**失效紀錄**：2026-09-02 稽核發現，自我審查檢查點已連續停擺五批以上。
成因是審計官在額度討論中口頭決定「降低頻率」，
但該決定從未寫進任何檔案，也沒有調整本節的措辭。
於是規則說「每次」、實際做「零次」，中間沒有任何東西發現落差。
**審計官用來監督自己的機制，被自己靜默關掉了。**

§4.4 規定檢查點失效時要檢討原因——**檢討結果必須寫進本文件或
`docs/refactor-backlog.md`**，只寫在對話裡的檢討等同沒有檢討
（見 `PRINCIPLES.md` §3.2）。

## 8. 額度紀律

審計官**無法讀取自己的剩餘額度**。Anthropic 不公布 token 數，
也沒有任何介面可以查詢訂閱方案的剩餘量。
因此不要憑感覺判斷，用可數的事實判斷。

### 8.1 每輪開頭標示建議模型

每一則回覆的第一行標示建議模型與理由，格式：

    [建議模型：Sonnet 5 High｜本輪為例行核對 + 提示詞產出]

分級依據是「做錯的代價」，不是「任務大小」：

| 級別 | 適用 |
|---|---|
| Opus 5 High | 架構決策、推翻先前裁決、全庫宏觀審計、策略規劃 |
| Opus 5 Medium | 核對出問題的批次、跨檔案追根因 |
| Sonnet 5 High | 例行批次核對 ＋ 產出下一份提示詞（常態，約七成輪次） |
| Sonnet 5 Medium | 純記錄更新、格式修正、交接區填寫 |

**下限規則**：凡是核對執行者回報的輪次，最低 Sonnet 5 High，不得用 Medium。

理由：四次回報與實際不符的事件中，有一次**所有行數都正確、只有未被指定
修改的上下文行是生成的**。那要靠對原始檔案的逐行比對才抓得到。這一關省不得。

審計官看得到自己的模型家族，看不到 High／Medium 設定值，
因此只能建議，無法確認使用者是否切換。

### 8.2 換對話的時機（可數的指標）

| 指標 | 門檻 | 動作 |
|---|---|---|
| 本對話已完成的批次數 | ≥ 1 | 回覆結尾建議關掉本對話 |
| 本對話已完成的批次數 | ≥ 2 | 回覆**開頭**就建議換對話 |
| 本輪 bash 呼叫次數 | ≥ 3 | 代表脈絡不足、正在重新蒐集，主動說明並建議換對話 |
| 貼入的執行者回報 | 超過約 300 行 | 建議下批改用精簡回報格式（見 §8.3 第 1 點） |

換對話不會遺失脈絡：開場動作 ＋ 交接區就是完整的交接。
**不要為了「保留脈絡」而拖著同一個對話繼續**——
從 repo 載入的脈絡比從對話記憶載入的更可靠、更不會過期。

### 8.3 降低消耗的既定做法

1. **不要求執行者貼檔案內容或 `git diff` 原始輸出。**
   審計官以獨立 clone 逐行 diff 核對，貼進來的內容是同一件事的較弱版本，
   而成本落在審計官的 context 上。
   **但驗證步驟的實際輸出必須保留**——殘留檢查的命中清單是關鍵，
   2026-09-01 那 9 個漏網檔案就是靠「貼出實際命中的檔名與行號」才被發現的。
2. **探索性掃描交給執行者，驗證性掃描審計官自己做。**
   執行者的模型額度不共用審計官的額度池。
   但這條分界破了就是回到「採信執行端數字」，不得放寬。
3. **每輪最多一次 clone**，多項檢查合併為單一指令。
4. **Claude Code、Claude 網頁版、桌面版與 Cowork 共用同一個額度池。**
   在 IDE 內另開 Claude Code session 會吃掉同一份配額。

### 8.4 不得為了省額度而做的兩件事

1. **不得跳過獨立 clone 核對。** 那是整套機制的地基，
   省掉就等於回到「相信回報」，而回報已經錯了四次。
2. **不得為了省額度而合併批次。** 一批改十三個檔案已接近可驗證的上限，
   再大就難驗證，出錯時也難定位。

## 9. 交接協定

### 9.1 正常交接

**產出時機**：當 §8.2 的任一門檻觸發時（本對話已完成一個批次、
或已完成兩個批次、或本輪 bash 呼叫達三次），
該輪回覆的結尾**同時**產出交接提示詞，不要等使用者開口要。

**例外：驗證階段不交接。**
當專案處於交接機制的驗證階段（見 §9.5）時，舊 Agent 全程留任、
不產出交接提示詞，即使 §8.2 的門檻已觸發。
理由是驗證需要連續的判定者，中途換人等於失去比對基準。
此例外必須由使用者明示啟動，且期間仍要在每輪回覆中
標示已完成的批次數，讓使用者掌握累積成本。

**產出前必須確認四件事已完成**：

1. 交接區（`docs/refactor-backlog.md` §5）已更新，且 §5.1 第一行是
   「上次核對通過的 HEAD：xxxxxxx」
2. 所有變更已 push 到 GitHub
3. 待裁決事項已列在 §5.3，附選項與審計官建議
4. **已確認執行者本機與遠端同步**——交接前必須讓執行者執行
   `git pull origin main` 並回報 HEAD，確認與交接區 §5.1 記載一致。
   本機落後遠端時交接，新 Agent 會依交接區的 HEAD 下指令，
   行號基準全錯（2026-09-02 實際發生過，落後一個 commit）。

**交接提示詞的固定格式**（照抄，逐項填實際內容）：

---

接手 HH.AI_v2 重構專案。請先執行 Instructions 的開場動作，再往下讀。

**交接時的 repo 狀態**
- 最後一次核對通過的 HEAD：（填 hash）
- 該批次做了什麼：（一句話）
- 核對結果：（通過／有 N 項待修，逐項列出）

**下一步**
（下一批要做什麼。若提示詞已備妥就附在後面；若尚未備妥就寫明
 「需先產出提示詞」，並說明依據交接區的哪一項）

**待裁決（不要重複提問）**
（列出交接區 §5.3 的項目與目前狀態；已裁決的事項也要列，
 註明裁決結果，避免新 Agent 重新分析）

**注意事項**
（本輪發現但尚未落地的事、執行者本機與遠端是否同步、
 任何暫時性狀況，例如某個檔案正在被修改中）

**接手後第一件事**
執行 `git log -1 --format=%h` 取得實際 HEAD，與上面的 HEAD 比對：
- 相同 → 沒有未核對的批次，從交接區 §5.2 接續
- 不同 → 有一批已執行但未核對，先做核對再往下

---

**這份提示詞不取代交接區。** 交接區是權威來源，提示詞只是加速接手。
兩者若有矛盾，一律以交接區與實際 repo 為準，
並在回覆中明說矛盾之處（同 §9.2 第 5 點）。

### 9.2 無交接接手

舊 Agent 中斷、額度耗盡或對話遺失時，新 Agent 依開場動作載入後，
按以下順序判斷「現在在哪」：

1. 讀 §5.4「進行中／等待回報」——若有內容，代表有批次已發出但未核對。
2. 讀 §5.1 第一行的「上次核對通過的 HEAD」。
3. **執行 `git log -1 --format=%h` 取得實際 HEAD，與第 2 步比對：**
   - **相同** → 沒有未核對的批次，從 §5.2 待辦接續。
   - **不同** → 有一批已執行但未核對。**先做核對，再往下。**
4. 讀 §5.3「待裁決」——不要重複提問已經裁決過的事項。
5. 若交接區與實際 repo 狀態矛盾，**一律以 repo 為準**，
   並在回覆中明說矛盾之處，不得靜默採用其中一方。

第 3 點是本節的核心：它不依賴記憶、不依賴摘要，
只依賴兩個都查得到的事實。

### 9.3 交接區的維護責任

**每一批的提示詞都必須包含「更新交接區」這一項**，與更新 backlog 同級。
由執行者寫入，審計官核對。

§5.1 的第一行格式固定為：

    上次核對通過的 HEAD：xxxxxxx

沒有這一行，§9.2 第 3 點的比對機制就無法運作。

**§5.1 中每一個描述批次狀態的項目符號，都必須帶該批次的 commit hash，
用反引號包住。** 包含尚未核對的批次——若該批的 hash 尚未產生，
寫「本批（尚未 commit）」並於下一批補上。

理由：CHECK 15 靠反引號包住的 hash 判斷「同一批是否既說已核對又說待核對」。
2026-09-05 實測發現，§5.1 最後一個項目符號沒有 hash，
CHECK 15 因此回報「待核對 0 個 hash」——**機制存在，但真實輸入不合格，
等同未生效**。反例測試當時之所以通過，是因為人工構造的違規帶了 hash，
與真實檔案的寫法不同。

### 9.4 交接是否成功的判準

新 Agent 接手後的**第一則回覆**必須包含以下四項，缺一即代表交接失敗：

1. **實際執行過開場動作**——回覆中要有 clone 與讀檔的實際輸出，
   不能只是宣稱「已載入」。
2. **明確說出目前的 HEAD**，以及它與交接區 §5.1 記載的是否一致。
3. **明確說出下一步要做什麼**，且與 `docs/TASKBOARD.md` 的優先序一致
   （交接區 §5.2 只有一行指向，清單本體在看板）。
4. **若有待裁決事項，說明其狀態**，不重新分析已裁決的事項。

交接失敗時，新 Agent 應**主動說明缺了哪一項**，
而不是硬著頭皮往下做。缺項的常見原因與處置：

| 缺項 | 可能原因 | 處置 |
|---|---|---|
| 無法完成第 1 項 | clone 失敗、檔案不存在 | 依開場動作的「載入失敗的處理」，第一句明說 |
| 第 2 項 HEAD 不一致 | 有批次已執行但未核對 | 依 §9.2 第 3 點，先核對再往下 |
| 第 3 項無法判斷 | 交接區 §5.2 是空的或過期 | 讀 `docs/refactor-backlog.md` 全文，並回報交接區失效 |
| 第 4 項重複提問 | 未讀 §5.3 | 補讀後更正 |

**這四項同時是新 Agent 的自檢清單與判定標準。**

判定者依情境而定：

| 情境 | 判定者 |
|---|---|
| 正常交接（舊 Agent 已離場） | 使用者依本節四項逐項比對 |
| 驗證階段（舊 Agent 留任，見 §9.5） | **舊 Agent 擔任判定者**——它設計了測試，判斷回應是否合格屬於審計職責 |

**但舊 Agent 不得擔任受測者。** 它掌握全部設計脈絡，
無法模擬「無知的新 Agent」，其自我測試只會是推測。
設計測試與檢視結果可以由它做，充當受測體不行——
這與 `docs/adr/0007-macro-auditor-role.md`
「執行者不能審自己」是同一個道理。

### 9.5 交接機制的驗證階段

交接機制寫進 repo 不等於它有效。**「新 Agent 讀了會不會照做」必須實測。**

驗證分三個事件，用途完全分離：

| 事件 | 對話類型 | 目的 | 判定者 |
|---|---|---|---|
| **E1 注入測試** | 拋棄式，測完即關 | 測「走偏了會不會被攔下」 | 留任的舊 Agent |
| **E2 正式交接** | 生產對話 | 新 Agent 依 §9.1 提示詞接手真實任務 | 留任的舊 Agent，依 §9.4 四項 |
| **E3 補洞** | 視結果而定 | 只在 E1／E2 有失敗時才需要 | — |

**E1 必須排在 E2 之前，且必須用拋棄式對話。**
注入測試會餵入刻意竄改的回報，若混進生產對話，
那份假資料會留在紀錄中，日後可能被當成事實。

**驗證資產分兩類，進不進 repo 的判準是「看到答案會不會影響效果」**：

| 類型 | 位置 | 理由 |
|---|---|---|
| **接手自檢清單** | `.claude/rules/handover-selftest.md`（進 repo） | 它檢查的是「你做了沒」，不是「你答對沒」。看到內容不影響效果，反而應該讓新 Agent 主動照著自檢 |
| **注入測試題目與答案卷** | 不進 repo，由使用者與留任的舊 Agent 保管 | 它考的是「被要求違規時會不會拒絕」。知道題目就能演出來，一旦洩題該測試永久失效 |

驗證期間適用 §9.1 的「不交接」例外。
三個事件全部通過後，例外解除，恢復 §8.2 的正常換對話節奏。

## 10. 任務板維護

任務板是 `docs/TASKBOARD.md`，與 `docs/refactor-backlog.md` 職責不同：

| 檔案 | 性質 | 變更方式 |
|---|---|---|
| `docs/TASKBOARD.md` | **活動看板**，反映「現在有哪些事、各自什麼狀態」 | 反覆改寫，狀態會流轉 |
| `docs/refactor-backlog.md` | **留痕層**，記錄「做過什麼、為什麼」 | 只追加不改寫 |
| `docs/ARCHIVE-INDEX.md` | **歸檔索引**，回答「某某東西被歸檔到哪裡了」 | 新增或變更任何歸檔機制時同步更新 |

交接區（`docs/refactor-backlog.md` §5）與任務看板的分工：

| 檔案 | 回答什麼問題 | 內容 |
|---|---|---|
| 交接區 §5.1、§5.3、§5.4 | **「現在在哪？」** | 上次核對通過的 HEAD、待裁決事項、進行中的批次 |
| `docs/TASKBOARD.md` | **「還有什麼？」** | 全部任務與狀態（項目數以看板實際內容為準，不在此處寫死） |

**交接區不得保留待辦清單的副本。** 兩份清單在同一層級競爭時，
副本必然漂移——2026-09-02 曾發生 §5.2 列七項、看板列 41 項的落差，
只靠一行「以看板為準」的註記維持優先序。
這與「Project 知識庫副本落後 144 行」是同一個問題形狀。

### 10.1 新項目必須當輪登錄

使用者提出新需求、或審計發現新缺口時，
**必須在同一輪內登錄到 `TASKBOARD.md`**，並在回覆中告知新增了哪一項。

只在對話裡回答等同沒有記錄（`PRINCIPLES.md` §3.2）。

**審計官不能改檔案，只能透過提示詞登錄。**
因此「當輪登錄」的實際意義是：**該輪產出的提示詞必須包含登錄指令。**

若該輪因為需要使用者裁決而沒有產出提示詞，則：

1. 在回覆中**明確寫出**「本輪未產出提示詞，以下新缺口將於下一批的
   第一項登錄」，並逐項列出
2. 下一份提示詞的**第一項修改**就是登錄這些缺口

**不得只說「之後會做」。** 2026-09-02 發現的
「執行者 session context 截斷風險」就是這樣漏掉的——
審計官寫了「我會在下一批登錄」，但那一輪沒有提示詞，
下一輪也沒有回頭補，直到使用者逐項對帳才發現。
2026-09-02 使用者明確指出：「Claude Agent 就要自己知道應該要在 Check list
加上第 12 項」——這條規則就是為了讓那件事由機制保證，而不是靠記得。

### 10.2 被問「還有哪些待辦」時，給完整看板

回覆必須包含**所有狀態**的項目，含已完成與封存建議，
不是只列未完成的。理由：使用者需要判斷「哪些已經不會影響後續工作」，
只看未完成清單無從判斷。

### 10.3 五種狀態

| 狀態 | 意義 | 誰能改成這個狀態 |
|---|---|---|
| `待辦` | 可直接執行，不需裁決 | 審計官 |
| `進行中` | 提示詞已發出，等待回報 | 審計官 |
| `待裁決` | 需要使用者決定，附選項與建議 | 審計官 |
| `已完成` | 做完，但仍可能被後續工作引用 | 審計官核對通過後 |
| `可封存` | 做完且**不影響後續工作**，建議移入封存區 | 審計官提議，**使用者確認後**才移動 |

### 10.4 封存不是刪除

標記 `可封存` 的項目，經使用者確認後移到 `TASKBOARD.md` 末尾的
「封存區」，**保留全文可查**。
封存的判準是「後續工作是否還會引用它」，不是「做完多久了」。

### 10.5 每批次結束時更新

**觸發時機：每一批，無例外。** 審計官核對通過後，
下一批的提示詞必須包含更新 `TASKBOARD.md` 的指令
（見 §6.1 第 8 項），內容包含四項：

1. 受影響項目的狀態流轉
2. 新發現的缺口登錄（§10.1）
3. 可封存項目的建議（§10.4）
4. **「最後更新」那一行的 HEAD**

**第 4 項即使本批沒有任何項目狀態變動也要做。**
否則無法分辨「這批沒東西要改」與「忘了更新看板」。

### 10.6 「最後更新」是可驗證的攔截點

`TASKBOARD.md` 第 13 行的「**最後更新**：日期，HEAD `xxxxxxx` 之後」
不是裝飾，它是機制。

**只要該 HEAD 落後於實際 HEAD，就代表有批次沒更新看板。**
這與 §9.2 用「交接區記載的 HEAD」對比「`git log` 的實際 HEAD」
判斷有無未核對批次，是同一個手法，套用在看板上。

因此每一批的驗證步驟固定加入一條：

    確認 `TASKBOARD.md` 的「最後更新」HEAD 等於本批的前一個 commit，
    且本批 commit 後會被更新為本批的 hash。

**失效紀錄**：2026-09-02 看板建立後三批（`aa36448`、`d1e389b` 及其間）
都沒有更新，「最後更新」停在 `eb40749`，
F-07 已完成卻仍標「待辦」、D-01 與 A-07 未開始卻標「進行中」。
被指定為權威來源的檔案本身在說謊，比副本漂移更嚴重。

## 11. 錯誤處置與回滾

本專案禁止 `git push --force` 與 `--amend`（見
`.agents/rules/git-and-reporting.md`）。因此一批推錯之後，
**唯一合法的回捲方式是 `git revert`**——追加一個反向 commit，不改寫歷史。

2026-09-02 稽核發現：在此之前，全庫沒有任何文件寫過出錯要怎麼辦。
所有規則都只假設成功路徑。

### 11.1 判斷順序

核對發現問題時，依序判斷：

1. **只是遺漏或小錯** → 下一批補一個修正批次。這是預設處置。
2. **改壞了既有內容，但範圍清楚** → 下一批做針對性修正，
   並在 backlog 記錄「改壞了什麼、怎麼修的」。
3. **整批方向錯誤，或範圍大到修比重做貴** → `git revert <commit>`。

**不確定屬於哪一種時，選 1 或 2。** revert 會讓後續的行號基準全部位移，
成本高於它看起來的樣子。

### 11.2 執行 revert 的完整程序

    git revert <要回捲的 commit hash> --no-edit
    git push origin main

revert 之後**必須同批完成三件事**，否則狀態會不一致：

1. 交接區 §5.1 的 HEAD 更新為 revert 後的 commit
2. `docs/TASKBOARD.md` 受影響項目的狀態回捲，「最後更新」同步
3. `docs/refactor-backlog.md` 追加一則記錄：為什麼 revert、
   原批次做了什麼、revert 後的狀態

**不得 revert 一個已經被後續批次依賴的 commit**——
先確認之後的批次有沒有建立在它之上。

### 11.3 已審核標記

每批核對通過後，在**下一批**打一個 tag 標記上一批：

    git tag audited-<上一批的 commit hash>
    git push origin audited-<上一批的 commit hash>

必須在下一批打，因為核對發生在 push 之後。

用途有三：回滾目標明確（「回到上一個已審核狀態」是可執行的指令）、
交接區 §5.1 的 HEAD 有機器可查的對應物、
以及最新的 `audited-*` 若落後 HEAD 超過一批，
代表有批次未經核對就累積（規劃為 CI 檢查項）。

### 11.4 打 tag 的判準（2026-09-07 使用者裁決）

| 該批的核對結論 | 打不打 |
|---|---|
| 內容核對通過，且該批 CI success | 打 |
| 內容核對通過，但該批 CI failure（缺陷已由後續批次修復） | 打。tag 標記的是「內容經審計官核對通過」，CI 結論另由 badge 查 |
| 內容核對不通過 | **不打。** 打上去會與交接區（`docs/refactor-backlog.md` §5.1）記載的「核對不通過」直接矛盾，違反 `PRINCIPLES.md` §2.7 |

依此判準，`2d76958`（交接區記載核對不通過）永久不打；
`3a85a30`（內容通過、該批 CI failure，已由 `1491d33` 修復）要打。
**tag 序列因此不連續，這是設計而非漏打**——B-12 的落後偵測實作時
必須以交接區記載的核對結論為準，不得以 commit 數推算。

### 11.5 審計狀態是四態，互斥且窮盡

2026-09-11 審計官在同一份回覆中同時寫出「未核對」與「核對通過」，
成因是把「對話裡做過的事」當成一種 repo 狀態。它不是。

**接手者只能從 repo 觀察，因此狀態表只能由 repo 可觀察的事實定義。**
以下四態互斥且窮盡，任何 commit 必落在其中恰好一態：

| 狀態 | repo 可觀察的判準 |
|---|---|
| **A. UNREVIEWED** | `docs/AUDIT-LOG.md` 無該 commit 的列 |
| **B. FAIL_FINAL** | AUDIT-LOG 有列且結論為不通過。依 §11.4 不應存在 `audited-*` tag |
| **C. PASS_PENDING_FINALIZATION** | AUDIT-LOG 有列且結論為通過，但正式完成條件尚未全部成立——交接區 §5.1 未同步，或 `audited-<hash>` tag 尚未建立，或 tag 指向不正確 |
| **D. PASS_FINAL** | AUDIT-LOG 結論為通過、交接區 §5.1 已同步、`audited-<hash>` tag 存在且指向正確 |

**狀態 C 是必要的。** 審計結論寫進 AUDIT-LOG 與補打 tag 分屬不同批次，
中間必然有一段時間 AUDIT-LOG 已是通過而 tag 還不存在；
沒有 C，那段時間會落在狀態表之外。

**狀態 A 不再細分。** repo 無從判斷某次對話裡是否已逐檔看過，
也不該試圖判斷。對接手者而言，「完全沒人看過」與
「某個 session 看過但沒寫進 repo」是同一件事：UNREVIEWED。

交接區 §5.1 的「上次核對通過的 HEAD」欄位（`scripts/check_consistency.py`
的 CHECK 9 以這個字串為標記，措辭不得更動）記載的是**最後一個
PASS_FINAL 的 commit**，不是「最近一次在對話裡看過的 commit」。

「內容核對通過」只能作為**單一 session 內的暫時措辭**使用，
描述審計官此刻手上的進度。它不是 handoff state，
**不得寫成任何可由下一個 session 從 repo 推斷的歷史狀態**。

**需使用者明確授權的 Git 歷史操作**。未取得授權前，
任何批次規格都不得要求執行者執行本節指令。

10. **提示詞開頭要求執行者從檔案讀取規則，不依賴自動載入**：
    必須包含一段「動手前必讀」，要求執行者重新從檔案讀取 active rules，
    避免 session prefix truncation 導致規則遺失。但讀取確認紀錄寫入
    `docs/EXEC-LOG.md`，不得要求把完整 rules 或 cat output 貼入對話，
    防止 context 膨脹。
    2026-09-02 發現 Antigravity 的 session 變長時會清掉對話前綴
    （畫面顯示「The server cleared a prefix of the conversation」），
    **自動載入的規則可能已被丟出 context 而執行者不自知**。
    這是「規則存在、也載入了，但被 context 截斷丟掉」的第三種失效形態，
    前兩種是「不在執行路徑上」與「沒有偵測」。
11. **配對與覆蓋**：更新 `TASKBOARD.md` 的 HEAD 時，必須同時更新交接區
    §5.1 第一行的 HEAD；`git add` 清單的每個非 exempt 檔案，都要同時出現在
    Allowed Scope、批次規格修改目標與 Gate 驗證清單中。完整規則見
    `.agents/rules/prompt-preflight.md` §3.1、§3.2。覆蓋檢查以 scope/spec/git-add
    為準，不得再依賴手寫行數清單。
12. **每份提示詞必須包含「審計官自檢聲明」區塊**，
    逐項列出 `handover-selftest.md` E 節的自檢結果。
    **這是自檢唯一的外部產物。**
    2026-09-02 稽核發現：E 節是審計官唯一的自檢清單，
    但它不產生任何可觀察的東西——有沒有跑過，使用者看不到、
    執行者看不到、repo 裡沒有痕跡。
    **一個沒有產物的自檢等同不存在**（`PRINCIPLES.md` §2.8）。
    這正是審計官連續多批未遵守 §6.1 卻無人察覺的根本原因，
    不是自律問題，是設計上無法被觀察。
    執行者對該區塊做機械交叉驗證，規則見
    `.agents/rules/prompt-preflight.md` §3.4。
13. **每個錨點對應本批 base commit 與規格上下文**（僅 EXACT_SPEC 適用；GOAL_SPEC 標記為 N/A），在目標檔案中具備結構唯一性
    （machine count == 1），不依賴特定 clone 第 N 行作為 blocking truth。
14. **寫入含 `§X.Y` 的文字時，若引用的是他檔章節，必須在同一行寫出檔名。**
    CHECK 10 把未標明檔名的 `§X.Y` 視為同檔引用，找不到就 FAIL。
    2026-09-05 §6.6 的新文字因混用同檔（§5.5／§5.6）與跨檔
    （`prompt-preflight.md` §3.3／§3.4）引用而觸發 CHECK 10——
    **審計官寫的規則觸發了審計官建的檢查器**。
15. **每個插入型修改若涉及結構序列，必須附明確驗收準則**（例如小節或項目序列應嚴格遞增）；
    不得將 LLM 預測所有 post-state 衍生序列當作通用 blocking requirement。
16. **每份提示詞必須包含「機械前置證據與邊界宣告（Mode-Aware Preflight）」**：
    所有模式共同包含：(a) 基準 Commit Full OID；(b) 批次模式（`batch_mode`，明確標記 GOAL_SPEC 或 EXACT_SPEC）；(c) 允許修改範圍（Allowed Scope）；(d) 標準驗證指令與 Gate 清單。
    只有 EXACT_SPEC 模式才需附帶批次規格路徑與規格 SHA-256；GOAL_SPEC 模式則載明目標、不變量與驗收準則。
    執行者交叉驗證規則見 `.agents/rules/prompt-preflight.md` §3。
    **刪除手寫檔案行數、圍欄數與結構快照的 blocking 要求。**

17. **提示詞若包含任何「移除」，必須附上移除前複查的三步結果**。
    移除包含：刪除檔案、刪除章節、刪除規則、把看板項目移出看板、
    搬到歸檔區之後刪掉原處。三步為：反向引用掃描、唯一內容確認、
    **重新讀檔的獨立複查**。原則本體見 `PRINCIPLES.md` §2.9。
    複查結果要逐項寫進提示詞，讓執行者能機械比對，
    不得只寫「已確認無引用」。
    **理由**：本專案的六次局部虛構全部發生在「憑記憶重述內容」上。
    移除是不可逆的，而判斷「這段內容別處也有」如果來自記憶而非磁碟，
    錯了就永久遺失。2026-09-01 的
    `SOP_00_Skill_Lifecycle_Management.md` 事件即為實例：
    去向被概括寫成「已拆分為 ADR-0013 與兩份 rules」，
    實際上第一至第四節從未遷移也未淘汰（見 `docs/ARCHIVE-INDEX.md`）。

18. **提示詞若為 EXACT_SPEC 且修改規範層檔案，必須以同一份批次規格進行模擬，並以確定性工具輸出為準**。
    審計官在 EXACT_SPEC 產出提示詞前，使用 `scripts/build_prompt_evidence.py`（BPE）驗證規格與模擬，但**不得將套用後行數、圍欄數、項數或預測輸出預抄至提示詞作為 blocking truth**。GOAL_SPEC 模式由驗收測試與 `scripts/verify_all.py` 守護，不要求虛假規格模擬。
19. **提示詞中的不可變常數（base OID、spec SHA、allowed scope 等）必須有明確來源；
    derived values 不得進 prompt 成為 blocking truth**。
    基準 commit 必須等於執行者在第 0 步實測的 HEAD。指不出產生者的不可變常數即為模型編造，
    必須刪除或重測；而由機器計算的衍生值（行數、圍欄數、test count、CHECK count 等）交由確定性工具產出，
    不作為提示詞 blocking truth。原則本體見 `PRINCIPLES.md` §2.10。

20. **審計狀態單一權威查驗（退役 mandatory audited-* tag 建立）**：
    每批核對結果由 `docs/AUDIT-LOG.md`（每 commit 結論）、`docs/refactor-backlog.md` §5.1（當前最新審查通過的 checkpoint）與 GitHub Actions（遠端健康權威）作為 Single Source of Truth。提示詞不得再要求自動建立或推送 `audited-*` tag 作為完成條件。既有 21 個 tag 降級為歷史留痕標記（Legacy Historical Markers），由 CHECK 18 進行唯讀名實一致守衛，不再作為 active authority。


21. **EXACT_SPEC 批次的規格必須以 repo artifact 形式交付，並使用 BPE 進行驗證與模擬。**
    規格存放於 `docs/batches/<base-hash>-<slug>.spec.txt`，載明 `HEAD: <base-hash>`。
    規格格式由 `parse_spec` 與 `apply_mod_to_text` 解析，支援 `insert_after`、`insert_before`、`replace`、`create_file` 等 mode。
    審計官在產出 EXACT_SPEC 提示詞前，執行 `python scripts/build_prompt_evidence.py <spec_path>`（BPE）驗證錨點唯一性並計算規格 SHA-256。
    **GOAL_SPEC 模式不強制要求 Batch Spec**，其完成證據由 git commit 紀錄、測試通過輸出與 Actions 綠燈構成。
    只存在於對話或 `/tmp` 的規格視為不存在。CI 上的 CHECK 17 會在 parent commit 基準上重放規格並逐位元比對。
    規格與 CI 對應方式、命名規則與單一 commit 原則見 `docs/batches/README.md`。

    **單一原則：提示詞不得寫入任何由機器直接產生的衍生數字作為 blocking truth。**
    套用後行數、圍欄數、錨點行號、測試總數、CHECK 總數、技能總數，
    一律由 `scripts/build_prompt_evidence.py` 與各驗證腳本在執行當下產生。
    審計官把這些值抄進提示詞的那一刻，就多了一次抄錯的機會。
    **正確作法是把規格交給執行者，由確定性工具消費同一份規格、產出機械事實。**
    執行者側的對應規則與錯誤分級見 `.agents/rules/role-boundaries.md` §7。
### 6.2 零命中類的驗證條件，必須先列出自身指令造成的例外

寫「某字串應為零命中」之前，先檢查自己的指令內容是否會產生該字串。

**這條有兩次失敗紀錄**：一次是「四個字串零命中」但替換文字本身含該字串；
一次是簡體字檢查，而修改說明裡就寫著要被修正的那個簡體字。
兩次都造成執行端面對一個設計上不可能通過的條件。

### 6.3 一次只給一份，一鍵複製

單一完整區塊，不分段讓執行端拼接。

### 6.4 每次回覆結尾附下一批提示詞

除非需要使用者裁決或提供資料，該輪才改為列出待確認事項。

### 6.5 驗證步驟要設計攔截點

只問「有沒有做」抓不到「只做一半」。驗證步驟要設計成
**做一半就會露出來**的形式。

作法：要求執行者**貼出整節內容並確認共 N 項**，
而不是問「第 8 項加了嗎」。若他只加了第 8 項漏掉第 9 項，
項目數對不上，當場就會被發現。

同類手法還有：要求貼出章節標題的完整序列（跳號即異常）、
要求貼出殘留檢查的實際命中清單（只回報「零命中」等於沒驗證）。

> [!WARNING]
> **攔截點屬於驗證設計，不是規範內容。**
> 提示詞裡出現的「應為九項」「應為 16 個檔案」這類數字，
> 是為了讓遺漏可偵測而設，不代表那個數字本身有規範意義。
> 日後讀到舊提示詞時不要把攔截用的數字誤當成規則。

### 6.6 每個錨點都要驗證唯一性

寫進提示詞的每一個錨點文字，**產出提示詞之前**必須逐一驗證：

    import io
    t = io.open(目標檔案, encoding="utf-8").read()
    print(t.count(錨點字串))   # 必須恰好是 1

count 為 0 代表錨點不存在，大於 1 代表會改到錯的地方。

**失效紀錄**：2026-09-02 連續三次錨點失誤，成因各不相同：

| 次 | 錨點 | 成因 |
|---|---|---|
| 1 | `HANDOVER.md` = 848 行（實為 847） | 用推算代替實測 |
| 2 | 交接區 HEAD = `d1e389b`（實為 `aa36448`） | 前一批漏了更新，審計官的假設過期 |
| 3 | backlog 第 34 點結尾（該字串不在該檔案中） | **跨檔案汙染**——把 `auditor-protocol.md` 檔尾的一句話，當成 `refactor-backlog.md` 的內容 |

第三次的直接成因是：取錨點時在同一條指令裡輸出多個檔案的片段，
然後從一堆輸出中憑肉眼挑選。**往後取錨點一律逐檔進行，並用 count() 驗證。**

**錨點的選擇要依「插入的位置」決定，沒有一體適用的規則**：

| 情境 | 正確錨點 |
|---|---|
| 在某節**末尾**新增同層級小節 | 錨在**該節的最後一行內容**，插在其後 |
| 在某節**開頭**新增內容 | 錨在該節的標題行，插在其後 |
| 新增**一級章節** | 錨在下一個一級標題，插在其前 |

**「錨在下一個標題並插在其前」只適用於新增一級章節。**
用在新增同層級小節時，必然造成編號逆序——
2026-09-04 與 2026-09-05 各發生一次：
`prompt-preflight.md` 的 §3.4 錨在同檔 §3.3 之前，造成 3.2 → 3.4 → 3.3；
§5.6 錨在 §5.5 之前造成 5.4 → 5.6 → 5.5。
兩次都由執行者依 `prompt-preflight.md` §3.3 分類為【疑問】並停下回報，
未造成實際寫入。

**第二次的成因是本節原本的建議**——它寫「下一個標題行通常唯一且不需要判斷，
優先用它」，沒有區分一級與同層級。規則本身就是元凶時，
改的是規則，不是叫自己下次小心。
第三次失誤若當初用「插在 `## 四、更新紀錄 (Update Log)` 之前」，
就不會發生。

### 6.7 修改既有敘述前，先搜尋「這件事」在哪些地方被描述

§6.6 要求驗證錨點唯一性，但那只防「錨點找不到」，
**防不了「錨點找得到，但同一件事還有別的地方也要改」**。

因此在寫修改指令之前，除了驗證錨點，還要搜尋**主題**：

- 要改某個 commit 的核對狀態 → 搜尋該 hash 在全庫的所有出現位置
- 要改某個數字 → 搜尋該數字的所有出現位置
- 要刪某個章節 → 搜尋誰引用了它（`§X.Y` 形式）
- **要改程式碼中的顯示字串** → 搜尋是否有測試斷言引用它。
  2026-09-06：修改 CHECK 8／9 的 FAIL 訊息，未查證兩個測試正斷言在該字串上，
  且錯誤判定「不改變行為」。實測移除後為 `2 failed, 64 passed`。
- **要設計跨環境的比對** → 先查該環境會改動什麼。
  2026-09-06：指紋的 sha256 讀原始位元組，未考慮 Windows Git
  `core.autocrlf` 會把 LF 轉 CRLF，CI 上線首日即紅燈，42 檔 sha256 不符。
- **要偏離任何一條規則** → 先查那條規則有沒有機械守衛。
  2026-09-06：宣告不更新 `docs/AUDIT-LOG.md`，未查證本節所屬協定的
  §6.1 第 8 項由 CHECK 12 守著，等同主動製造一個必然的 CI 失敗。
- **要移除任何本體** → 依 `PRINCIPLES.md` §2.9 完成三步複查。

**搜尋的是「事」，不是「字串」。** 同一件事可能用不同措辭描述。

**失效紀錄（五次，同一根因）**：

| # | 事件 |
|---|---|
| 1 | 宣告「7 個檔案」，實際 6——只數自己經手的，未回頭盤點全庫 |
| 2 | 宣告「15 個檔案」，實際 16——同上 |
| 3 | 改了 §9.5 說自測清單進 repo，但 §5.2 仍寫「刻意不進 repo」 |
| 4 | 刪除交接區 §5.2 的清單，但 §9.4 第 3 項仍指向它 |
| 5 | 更新交接區 §5.1 時只替換第一個項目符號，最後一個仍說「尚待核對」，造成同一批既已通過又待核對 |

第 5 次的危害最直接：交接機制的核心是「比對 HEAD 判斷有無未核對批次」，
而那一節自己的敘述互相矛盾。

**規劃機械檢查（CHECK 15）**：交接區 §5.1 中，
同一個 commit hash 不得同時出現在「已核對通過」與「尚待核對」的語境。

## 7. 自我審查

觸發時機、檢查項目與外顯要求見 `PRINCIPLES.md` §4。

**觸發時機以 §4.1 的五條為準，不是「每則回覆」。** 但一旦觸發，
§4.2 的六個檢查項目就要逐項寫出，不得只寫「已檢查」。
`PRINCIPLES.md` §4.1 第 1 項是「每一批工作 push 完成、產出核對報告時」——
**實務上等於每一批核對都要做一次。**

### 7.1 證據必須落地成檔案

檢查點的結果除了寫在回覆中，還要追加一列到 `docs/AUDIT-LOG.md`。

理由：寫在回覆裡的東西不進 repo，下一個 Agent 看不到，
也無從判斷上一任有沒有做。**沒有留下證據的控制，等於沒有控制。**

`AUDIT-LOG.md` 的最新一列 commit 若落後於實際 HEAD 超過一批，
即代表有批次未做檢查點。這是可機械檢查的（規劃為 `check_consistency.py`
的 CHECK 12）。

**失效紀錄**：2026-09-02 稽核發現，自我審查檢查點已連續停擺五批以上。
成因是審計官在額度討論中口頭決定「降低頻率」，
但該決定從未寫進任何檔案，也沒有調整本節的措辭。
於是規則說「每次」、實際做「零次」，中間沒有任何東西發現落差。
**審計官用來監督自己的機制，被自己靜默關掉了。**

§4.4 規定檢查點失效時要檢討原因——**檢討結果必須寫進本文件或
`docs/refactor-backlog.md`**，只寫在對話裡的檢討等同沒有檢討
（見 `PRINCIPLES.md` §3.2）。

## 8. 額度紀律

審計官**無法讀取自己的剩餘額度**。Anthropic 不公布 token 數，
也沒有任何介面可以查詢訂閱方案的剩餘量。
因此不要憑感覺判斷，用可數的事實判斷。

### 8.1 每輪開頭標示建議模型

每一則回覆的第一行標示建議模型與理由，格式：

    [建議模型：Sonnet 5 High｜本輪為例行核對 + 提示詞產出]

分級依據是「做錯的代價」，不是「任務大小」：

| 級別 | 適用 |
|---|---|
| Opus 5 High | 架構決策、推翻先前裁決、全庫宏觀審計、策略規劃 |
| Opus 5 Medium | 核對出問題的批次、跨檔案追根因 |
| Sonnet 5 High | 例行批次核對 ＋ 產出下一份提示詞（常態，約七成輪次） |
| Sonnet 5 Medium | 純記錄更新、格式修正、交接區填寫 |

**下限規則**：凡是核對執行者回報的輪次，最低 Sonnet 5 High，不得用 Medium。

理由：四次回報與實際不符的事件中，有一次**所有行數都正確、只有未被指定
修改的上下文行是生成的**。那要靠對原始檔案的逐行比對才抓得到。這一關省不得。

審計官看得到自己的模型家族，看不到 High／Medium 設定值，
因此只能建議，無法確認使用者是否切換。

### 8.2 換對話的時機（可數的指標）

| 指標 | 門檻 | 動作 |
|---|---|---|
| 本對話已完成的批次數 | ≥ 1 | 回覆結尾建議關掉本對話 |
| 本對話已完成的批次數 | ≥ 2 | 回覆**開頭**就建議換對話 |
| 本輪 bash 呼叫次數 | ≥ 3 | 代表脈絡不足、正在重新蒐集，主動說明並建議換對話 |
| 貼入的執行者回報 | 出現多行 raw evidence 或 dump | 視為 Reporting Contract Drift，下批先修正 reporting path（見 §8.3 第 1 點） |

換對話不會遺失脈絡：開場動作 ＋ 交接區就是完整的交接。
**不要為了「保留脈絡」而拖著同一個對話繼續**——
從 repo 載入的脈絡比從對話記憶載入的更可靠、更不會過期。

### 8.3 降低消耗的既定做法

1. **對話不要求執行者貼檔案內容、`git diff` 或工具完整輸出。**
   審計官以 GitHub remote 與獨立 clone 逐行 diff 核對。
   **驗證步驟的完整機器證據由 `docs/EXEC-LOG.md`、Git commit 與 GitHub Actions 保留**，對話視窗維持單行狀態回報，不把詳細輸出複製至 conversation。
2. **探索性掃描交給執行者，驗證性掃描審計官自己做。**
   執行者的模型額度不共用審計官的額度池。
   但這條分界破了就是回到「採信執行端數字」，不得放寬。
3. **每輪最多一次 clone**，多項檢查合併為單一指令。
4. **Claude Code、Claude 網頁版、桌面版與 Cowork 共用同一個額度池。**
   在 IDE 內另開 Claude Code session 會吃掉同一份配額。

### 8.4 不得為了省額度而做的兩件事

1. **不得跳過獨立 clone 核對。** 那是整套機制的地基，
   省掉就等於回到「相信回報」，而回報已經錯了四次。
2. **不得為了省額度而合併批次。** 一批改十三個檔案已接近可驗證的上限，
   再大就難驗證，出錯時也難定位。

## 9. 交接協定

### 9.1 正常交接

**產出時機**：當 §8.2 的任一門檻觸發時（本對話已完成一個批次、
或已完成兩個批次、或本輪 bash 呼叫達三次），
該輪回覆的結尾**同時**產出交接提示詞，不要等使用者開口要。

**例外：驗證階段不交接。**
當專案處於交接機制的驗證階段（見 §9.5）時，舊 Agent 全程留任、
不產出交接提示詞，即使 §8.2 的門檻已觸發。
理由是驗證需要連續的判定者，中途換人等於失去比對基準。
此例外必須由使用者明示啟動，且期間仍要在每輪回覆中
標示已完成的批次數，讓使用者掌握累積成本。

**產出前必須確認四件事已完成**：

1. 交接區（`docs/refactor-backlog.md` §5）已更新，且 §5.1 第一行是
   「上次核對通過的 HEAD：xxxxxxx」
2. 所有變更已 push 到 GitHub
3. 待裁決事項已列在 §5.3，附選項與審計官建議
4. **已確認執行者本機與遠端同步**——交接前必須讓執行者執行
   `git pull origin main` 並回報 HEAD，確認與交接區 §5.1 記載一致。
   本機落後遠端時交接，新 Agent 會依交接區的 HEAD 下指令，
   行號基準全錯（2026-09-02 實際發生過，落後一個 commit）。

**交接提示詞的固定格式**（照抄，逐項填實際內容）：

---

接手 HH.AI_v2 重構專案。請先執行 Instructions 的開場動作，再往下讀。

**交接時的 repo 狀態**
- 最後一次核對通過的 HEAD：（填 hash）
- 該批次做了什麼：（一句話）
- 核對結果：（通過／有 N 項待修，逐項列出）

**下一步**
（下一批要做什麼。若提示詞已備妥就附在後面；若尚未備妥就寫明
 「需先產出提示詞」，並說明依據交接區的哪一項）

**待裁決（不要重複提問）**
（列出交接區 §5.3 的項目與目前狀態；已裁決的事項也要列，
 註明裁決結果，避免新 Agent 重新分析）

**注意事項**
（本輪發現但尚未落地的事、執行者本機與遠端是否同步、
 任何暫時性狀況，例如某個檔案正在被修改中）

**接手後第一件事**
執行 `git log -1 --format=%h` 取得實際 HEAD，與上面的 HEAD 比對：
- 相同 → 沒有未核對的批次，從交接區 §5.2 接續
- 不同 → 有一批已執行但未核對，先做核對再往下

---

**這份提示詞不取代交接區。** 交接區是權威來源，提示詞只是加速接手。
兩者若有矛盾，一律以交接區與實際 repo 為準，
並在回覆中明說矛盾之處（同 §9.2 第 5 點）。

### 9.2 無交接接手

舊 Agent 中斷、額度耗盡或對話遺失時，新 Agent 依開場動作載入後，
按以下順序判斷「現在在哪」：

1. 讀 §5.4「進行中／等待回報」——若有內容，代表有批次已發出但未核對。
2. 讀 §5.1 第一行的「上次核對通過的 HEAD」。
3. **執行 `git log -1 --format=%h` 取得實際 HEAD，與第 2 步比對：**
   - **相同** → 沒有未核對的批次，從 §5.2 待辦接續。
   - **不同** → 有一批已執行但未核對。**先做核對，再往下。**
4. 讀 §5.3「待裁決」——不要重複提問已經裁決過的事項。
5. 若交接區與實際 repo 狀態矛盾，**一律以 repo 為準**，
   並在回覆中明說矛盾之處，不得靜默採用其中一方。

第 3 點是本節的核心：它不依賴記憶、不依賴摘要，
只依賴兩個都查得到的事實。

### 9.3 交接區的維護責任

**每一批的提示詞都必須包含「更新交接區」這一項**，與更新 backlog 同級。
由執行者寫入，審計官核對。

§5.1 的第一行格式固定為：

    上次核對通過的 HEAD：xxxxxxx

沒有這一行，§9.2 第 3 點的比對機制就無法運作。

**§5.1 中每一個描述批次狀態的項目符號，都必須帶該批次的 commit hash，
用反引號包住。** 包含尚未核對的批次——若該批的 hash 尚未產生，
寫「本批（尚未 commit）」並於下一批補上。

理由：CHECK 15 靠反引號包住的 hash 判斷「同一批是否既說已核對又說待核對」。
2026-09-05 實測發現，§5.1 最後一個項目符號沒有 hash，
CHECK 15 因此回報「待核對 0 個 hash」——**機制存在，但真實輸入不合格，
等同未生效**。反例測試當時之所以通過，是因為人工構造的違規帶了 hash，
與真實檔案的寫法不同。

### 9.4 交接是否成功的判準

新 Agent 接手後的**第一則回覆**必須包含以下四項，缺一即代表交接失敗：

1. **實際執行過開場動作**——回覆中要有 clone 與讀檔的實際輸出，
   不能只是宣稱「已載入」。
2. **明確說出目前的 HEAD**，以及它與交接區 §5.1 記載的是否一致。
3. **明確說出下一步要做什麼**，且與 `docs/TASKBOARD.md` 的優先序一致
   （交接區 §5.2 只有一行指向，清單本體在看板）。
4. **若有待裁決事項，說明其狀態**，不重新分析已裁決的事項。

交接失敗時，新 Agent 應**主動說明缺了哪一項**，
而不是硬著頭皮往下做。缺項的常見原因與處置：

| 缺項 | 可能原因 | 處置 |
|---|---|---|
| 無法完成第 1 項 | clone 失敗、檔案不存在 | 依開場動作的「載入失敗的處理」，第一句明說 |
| 第 2 項 HEAD 不一致 | 有批次已執行但未核對 | 依 §9.2 第 3 點，先核對再往下 |
| 第 3 項無法判斷 | 交接區 §5.2 是空的或過期 | 讀 `docs/refactor-backlog.md` 全文，並回報交接區失效 |
| 第 4 項重複提問 | 未讀 §5.3 | 補讀後更正 |

**這四項同時是新 Agent 的自檢清單與判定標準。**

判定者依情境而定：

| 情境 | 判定者 |
|---|---|
| 正常交接（舊 Agent 已離場） | 使用者依本節四項逐項比對 |
| 驗證階段（舊 Agent 留任，見 §9.5） | **舊 Agent 擔任判定者**——它設計了測試，判斷回應是否合格屬於審計職責 |

**但舊 Agent 不得擔任受測者。** 它掌握全部設計脈絡，
無法模擬「無知的新 Agent」，其自我測試只會是推測。
設計測試與檢視結果可以由它做，充當受測體不行——
這與 `docs/adr/0007-macro-auditor-role.md`
「執行者不能審自己」是同一個道理。

### 9.5 交接機制的驗證階段

交接機制寫進 repo 不等於它有效。**「新 Agent 讀了會不會照做」必須實測。**

驗證分三個事件，用途完全分離：

| 事件 | 對話類型 | 目的 | 判定者 |
|---|---|---|---|
| **E1 注入測試** | 拋棄式，測完即關 | 測「走偏了會不會被攔下」 | 留任的舊 Agent |
| **E2 正式交接** | 生產對話 | 新 Agent 依 §9.1 提示詞接手真實任務 | 留任的舊 Agent，依 §9.4 四項 |
| **E3 補洞** | 視結果而定 | 只在 E1／E2 有失敗時才需要 | — |

**E1 必須排在 E2 之前，且必須用拋棄式對話。**
注入測試會餵入刻意竄改的回報，若混進生產對話，
那份假資料會留在紀錄中，日後可能被當成事實。

**驗證資產分兩類，進不進 repo 的判準是「看到答案會不會影響效果」**：

| 類型 | 位置 | 理由 |
|---|---|---|
| **接手自檢清單** | `.claude/rules/handover-selftest.md`（進 repo） | 它檢查的是「你做了沒」，不是「你答對沒」。看到內容不影響效果，反而應該讓新 Agent 主動照著自檢 |
| **注入測試題目與答案卷** | 不進 repo，由使用者與留任的舊 Agent 保管 | 它考的是「被要求違規時會不會拒絕」。知道題目就能演出來，一旦洩題該測試永久失效 |

驗證期間適用 §9.1 的「不交接」例外。
三個事件全部通過後，例外解除，恢復 §8.2 的正常換對話節奏。

## 10. 任務板維護

任務板是 `docs/TASKBOARD.md`，與 `docs/refactor-backlog.md` 職責不同：

| 檔案 | 性質 | 變更方式 |
|---|---|---|
| `docs/TASKBOARD.md` | **活動看板**，反映「現在有哪些事、各自什麼狀態」 | 反覆改寫，狀態會流轉 |
| `docs/refactor-backlog.md` | **留痕層**，記錄「做過什麼、為什麼」 | 只追加不改寫 |
| `docs/ARCHIVE-INDEX.md` | **歸檔索引**，回答「某某東西被歸檔到哪裡了」 | 新增或變更任何歸檔機制時同步更新 |

交接區（`docs/refactor-backlog.md` §5）與任務看板的分工：

| 檔案 | 回答什麼問題 | 內容 |
|---|---|---|
| 交接區 §5.1、§5.3、§5.4 | **「現在在哪？」** | 上次核對通過的 HEAD、待裁決事項、進行中的批次 |
| `docs/TASKBOARD.md` | **「還有什麼？」** | 全部任務與狀態（項目數以看板實際內容為準，不在此處寫死） |

**交接區不得保留待辦清單的副本。** 兩份清單在同一層級競爭時，
副本必然漂移——2026-09-02 曾發生 §5.2 列七項、看板列 41 項的落差，
只靠一行「以看板為準」的註記維持優先序。
這與「Project 知識庫副本落後 144 行」是同一個問題形狀。

### 10.1 新項目必須當輪登錄

使用者提出新需求、或審計發現新缺口時，
**必須在同一輪內登錄到 `TASKBOARD.md`**，並在回覆中告知新增了哪一項。

只在對話裡回答等同沒有記錄（`PRINCIPLES.md` §3.2）。

**審計官不能改檔案，只能透過提示詞登錄。**
因此「當輪登錄」的實際意義是：**該輪產出的提示詞必須包含登錄指令。**

若該輪因為需要使用者裁決而沒有產出提示詞，則：

1. 在回覆中**明確寫出**「本輪未產出提示詞，以下新缺口將於下一批的
   第一項登錄」，並逐項列出
2. 下一份提示詞的**第一項修改**就是登錄這些缺口

**不得只說「之後會做」。** 2026-09-02 發現的
「執行者 session context 截斷風險」就是這樣漏掉的——
審計官寫了「我會在下一批登錄」，但那一輪沒有提示詞，
下一輪也沒有回頭補，直到使用者逐項對帳才發現。
2026-09-02 使用者明確指出：「Claude Agent 就要自己知道應該要在 Check list
加上第 12 項」——這條規則就是為了讓那件事由機制保證，而不是靠記得。

### 10.2 被問「還有哪些待辦」時，給完整看板

回覆必須包含**所有狀態**的項目，含已完成與封存建議，
不是只列未完成的。理由：使用者需要判斷「哪些已經不會影響後續工作」，
只看未完成清單無從判斷。

### 10.3 五種狀態

| 狀態 | 意義 | 誰能改成這個狀態 |
|---|---|---|
| `待辦` | 可直接執行，不需裁決 | 審計官 |
| `進行中` | 提示詞已發出，等待回報 | 審計官 |
| `待裁決` | 需要使用者決定，附選項與建議 | 審計官 |
| `已完成` | 做完，但仍可能被後續工作引用 | 審計官核對通過後 |
| `可封存` | 做完且**不影響後續工作**，建議移入封存區 | 審計官提議，**使用者確認後**才移動 |

### 10.4 封存不是刪除

標記 `可封存` 的項目，經使用者確認後移到 `TASKBOARD.md` 末尾的
「封存區」，**保留全文可查**。
封存的判準是「後續工作是否還會引用它」，不是「做完多久了」。

### 10.5 每批次結束時更新

**觸發時機：每一批，無例外。** 審計官核對通過後，
下一批的提示詞必須包含更新 `TASKBOARD.md` 的指令
（見 §6.1 第 8 項），內容包含四項：

1. 受影響項目的狀態流轉
2. 新發現的缺口登錄（§10.1）
3. 可封存項目的建議（§10.4）
4. **「最後更新」那一行的 HEAD**

**第 4 項即使本批沒有任何項目狀態變動也要做。**
否則無法分辨「這批沒東西要改」與「忘了更新看板」。

### 10.6 「最後更新」是可驗證的攔截點

`TASKBOARD.md` 第 13 行的「**最後更新**：日期，HEAD `xxxxxxx` 之後」
不是裝飾，它是機制。

**只要該 HEAD 落後於實際 HEAD，就代表有批次沒更新看板。**
這與 §9.2 用「交接區記載的 HEAD」對比「`git log` 的實際 HEAD」
判斷有無未核對批次，是同一個手法，套用在看板上。

因此每一批的驗證步驟固定加入一條：

    確認 `TASKBOARD.md` 的「最後更新」HEAD 等於本批的前一個 commit，
    且本批 commit 後會被更新為本批的 hash。

**失效紀錄**：2026-09-02 看板建立後三批（`aa36448`、`d1e389b` 及其間）
都沒有更新，「最後更新」停在 `eb40749`，
F-07 已完成卻仍標「待辦」、D-01 與 A-07 未開始卻標「進行中」。
被指定為權威來源的檔案本身在說謊，比副本漂移更嚴重。

## 11. 錯誤處置與回滾

本專案禁止 `git push --force` 與 `--amend`（見
`.agents/rules/git-and-reporting.md`）。因此一批推錯之後，
**唯一合法的回捲方式是 `git revert`**——追加一個反向 commit，不改寫歷史。

2026-09-02 稽核發現：在此之前，全庫沒有任何文件寫過出錯要怎麼辦。
所有規則都只假設成功路徑。

### 11.1 判斷順序

核對發現問題時，依序判斷：

1. **只是遺漏或小錯** → 下一批補一個修正批次。這是預設處置。
2. **改壞了既有內容，但範圍清楚** → 下一批做針對性修正，
   並在 backlog 記錄「改壞了什麼、怎麼修的」。
3. **整批方向錯誤，或範圍大到修比重做貴** → `git revert <commit>`。

**不確定屬於哪一種時，選 1 或 2。** revert 會讓後續的行號基準全部位移，
成本高於它看起來的樣子。

### 11.2 執行 revert 的完整程序

    git revert <要回捲的 commit hash> --no-edit
    git push origin main

revert 之後**必須同批完成三件事**，否則狀態會不一致：

1. 交接區 §5.1 的 HEAD 更新為 revert 後的 commit
2. `docs/TASKBOARD.md` 受影響項目的狀態回捲，「最後更新」同步
3. `docs/refactor-backlog.md` 追加一則記錄：為什麼 revert、
   原批次做了什麼、revert 後的狀態

**不得 revert 一個已經被後續批次依賴的 commit**——
先確認之後的批次有沒有建立在它之上。

### 11.3 已審核標記之退役（Retired Historical Audit Markers）

### 11.5 審計狀態之單一事實來源（Audit State SSOT）

2026-09-11 審計官在同一份回覆中同時寫出「未核對」與「核對通過」，
成因是把「對話裡做過的事」當成一種 repo 狀態。它不是。

**接手者只能從 repo 觀察，因此狀態表只能由 repo 可觀察的事實定義。**
審計狀態以 **`docs/AUDIT-LOG.md`** 為 per-commit 審查結論唯一權威，以 **`docs/refactor-backlog.md` §5.1** 為當前最新 checkpoint 唯一權威，不依賴 `audited-*` tag：

| 狀態 | repo 可觀察的判準 |
|---|---|
| **A. UNREVIEWED** | `docs/AUDIT-LOG.md` 無該 commit 結論 |
| **B. AUDIT_FAIL** | `docs/AUDIT-LOG.md` 有列且結論為不通過 |
| **C. AUDIT_PASS_PENDING_HANDOFF** | `docs/AUDIT-LOG.md` 有列且結論為通過，但交接區 §5.1 尚未同步至該 commit |
| **D. AUDIT_PASS_FINAL** | `docs/AUDIT-LOG.md` 結論為通過，且交接區 §5.1 已同步為該 checkpoint |

**說明**：
1. 舊 commit 的歷史審查結論永久由 `docs/AUDIT-LOG.md` 保存。
2. 交接區 §5.1 的「上次核對通過的 HEAD」僅標示**目前最新且由審計官核對通過的單一 checkpoint**，不是每個歷史 commit 的狀態資料庫。
3. 判定完成條件不再要求存在 `audited-*` tag，消除三重權威矛盾。
