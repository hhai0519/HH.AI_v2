# ADR-0007: 宏觀審計官角色定位

- Status: Accepted
- Date: 2026-08-17

## Context

隨著遷移批次增加（目前已完成 14 個技能），開始出現單一批次內部核對不到、
但跨批次累積後才顯現的問題，例如：`agency-orchestrator` 的路由說明沒有
同步新增的 `agents/` bucket 技能（拓撲斷鏈的一種）、新舊批次之間
frontmatter 的 `name` 欄位引號寫法不一致（介面不一致）。這些問題單看
一個批次看不出來，需要有一個獨立於「執行遷移」之外的角色，定期對整個
技能庫做全域性的健康檢查。

使用者參考社群上一份「Antigravity Macro Auditor」規劃書，提出四個審計
維度（拓撲完整性、介面一致性、冗餘與收斂、技術鎖定 Scope Lock）與標準化
報告格式，要求正式定義這個角色。

## Decision

### 由誰執行審計

**宏觀審計官由使用者對話中的 Claude 擔任，不由執行遷移的 Antigravity Agent
自己兼任。** 這是核心決策，理由見下方 Consequences 第一點。Antigravity
負責遷移執行與初步的個別技能核對（三層核對，見 ADR-0005），宏觀審計官
在每批次完成 push 後，**獨立 clone 實際 GitHub repo**，核對真實檔案內容，
不依賴 Antigravity 自己產出的文字報告作為審計依據。

### 四個審計維度

1. **拓撲完整性 (Topology)**：驗證依賴圖譜與調度鏈路——`dependencies`、
   內文中提到的技能引用、路由技能（如 `agency-orchestrator`）的角色列表，
   是否都指向實際存在的技能實體。檢查三種問題：
   - 斷鏈：引用了不存在或已改名的技能
   - 孤島：存在但從未被任何其他技能或路由引用的技能
   - 循環依賴：A 呼叫 B、B 呼叫 C、C 又呼叫回 A 的死循環調度
2. **介面一致性 (Interface)**：frontmatter 欄位命名、YAML 寫法慣例
   （例如是否加引號）、bucket 標籤格式（如根目錄 README 的
   `` (`bucket`) `` 反引號寫法）是否跨技能、跨批次保持一致。
3. **冗餘與收斂 (Redundancy)**：偵測技能之間功能重疊過高的候選整併對象，
   **只產出裁決建議，不擅自合併**——實際整併仍需使用者確認後才執行
   （比照 `agency-orchestrator` 合併 `reflection-module` 的既有做法）。
4. **技術鎖定 (Scope Lock)**：審計階段嚴禁主動建議引入未經討論的新框架
   或外部工具。**但這不代表不能指出「這裡已經斷了/過時了」**——指出
   `Persona Knowledge MCP` 指向不存在的伺服器、或某個依賴已被官方標記
   歸檔，屬於診斷職責範圍內；「建議換成某個新方案」則不在審計範圍內，
   需要另外開獨立討論（見「技能適用性研究」的既有共識：不併入遷移主線）。

### Gatekeeping 規則

若審計發現斷鏈或重大命名/格式不一致，**該批次不算正式定案**，需要先修復
才能進入下一批次。這跟既有的三層核對流程（ADR-0005）是同一個精神的延伸，
只是把檢查範圍從「單一批次內部」擴大到「跨批次的全域一致性」。
